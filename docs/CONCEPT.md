# GhostLift — コンセプト設計

## 掛け算の2語

> **「広告出稿 × 需要の増分」 — そのコンバージョンは、広告が作ったのか、数えただけか**

片方は「情報」（誰に、どんな言葉を、どうやって届けるか）。
もう片方は「資源」（限られた在庫と、限られた財布）。
このあいだに起きる連鎖が、このシミュレーションの観測対象です。

## 問い

広告を配信したあと、広告プラットフォームは「このコンバージョンは広告の成果です」と報告する。
その報告の中身は、本当は何でできているのか。

- 広告が**本当に生んだ**購買
- **競合から奪った**だけの購買（ブランドには増分、市場には増分ゼロ）
- 広告がなくても**どうせ買っていた**人の購買（＝幽霊。広告費だけが出ていく）

そして誰も報告しないもの:

- 広告のせいで**失われた**購買（在庫が先に枯れる、押しつけがましさで離れる）

## なぜシミュレーションでしかできないのか

広告効果測定の根本問題は、**同じ人物の「広告を見た場合」と「見なかった場合」を同時に観測できない**ことです。
A/Bテストをしても、比べているのは別々の人の集団であって、同じ人の2つの人生ではありません。

このシミュレーションでは、それができます。

同一シードから同じ8人・同じ初期配置・同じ性格・同じ財布を生成し、
**広告のある世界とない世界を並走させ、agent 3 と agent 3 を突き合わせる**。
この対応づけが、GhostLift の存在理由そのものです。

さらに、LLM のサンプラも同じシードに固定してあるため、
**広告が着弾するステップまで、2つの世界はビット単位で同一**になります。
つまり step 4 以降に現れた差分は、定義上すべて広告に起因します。

> 本家 SD-AgentFoundry-2D は「初期位置と性格が毎回ランダムで、シード固定の項目がない」と
> READMEに明記された仕様です。GhostLift はここを拡張しました。詳細は README の「本家からの差分」。

## 誰の何を解決するプロダクトか

- **EC・広告運用者**: 「ROAS 400%」という報告のうち、どれだけが幽霊なのかを事前にリハーサルできる。
  とくに**リターゲティングの罠**——すでに買う気の人にだけ配信すれば見かけの数字は最高になるが、
  純増はゼロに近づく——を、実際に予算を溶かす前に体験できる
- **経営判断**: 広告予算を止めたら売上がいくら落ちるのか、を止める前に問える
- **情報空間の効果測定一般**: 「その行動変容は、情報が起こしたのか、起きるはずだった行動を
  数えただけなのか」という問いは、広告に限らない。影響工作や公共キャンペーンの評価と同じ構造
- 出力は**検証済みの人間行動予測ではなく、仮説生成の道具**（本家の解釈上の注意に準拠）

## シミュレーションで何を観測するか（観測指標）

1. **BrandCo の累計購入数**（世界ごと・ステップごと）
2. **エージェント単位の購買結果**（どの店で買ったか、買わなかったか）

2 を2つの世界で突き合わせると、冒頭の4分類がそのまま出ます。
これが唯一の主要成果物で、`scripts/ghost_analysis.py` がこの分解を行います。

## 世界のマッピング

| ベース（SD-AgentFoundry-2D）の部品 | GhostLift での割り当て |
|---|---|
| エージェント | 消費者 8人。それぞれ **予算（数値）** を持つ |
| 場所（places） | 店2軒: `brandco`（広告主）と `rival`（競合） |
| 場所の数値（capacity） | **在庫 `stock` と 価格 `price`**。店内にいる人だけが残数を知れる |
| 局所イベント（fires） | 未使用 |
| **全域イベント** | **広告 `ad_campaigns`**。ターゲティング指定つき |
| 口コミ（messages） | そのまま。オーガニック需要の伝播 |
| — | **新アクション `buy`**。買うかどうかは LLM の判断 |

### 設計上の要点: 火事と広告の対称性

本家の火事は「**距離で決まる**知覚」——半径内の人だけが知る。
GhostLift の広告は「**ターゲティングで決まる**配信」——狙った人だけに届く。

同じ「一部の人だけが知る外部ショック」でも、**誰が知るかを決めるのが自然法則か広告主か**が違う。
この対称性が、広告というものの本質だと考えて設計しました。

### 買うかどうかは、プログラムしていない

エージェントに与えるのは数値だけです。予算、価格、店内の残り在庫、そして広告の文面。
「安いから買え」「品薄だから急げ」といった判断は一切書いていません。
`buy` アクションを選ぶかどうかは、毎ステップ LLM が決めます。

## 3つのシナリオ = 介入点

3つの設定ファイルの差は **`ad_campaigns` ブロックだけ**です。
世界も、人も、財布も、在庫も、シードも同一。

| シナリオ | 内容 | 介入点 |
|---|---|---|
| A `scenario_noad.yaml` | 広告なし | — （反実仮想の基準） |
| B `scenario_broadcast.yaml` | 全員に配信 | 予算を「広く薄く」 |
| C `scenario_retarget.yaml` | 店から半径6以内の人だけに配信 | 予算を「もう買う気の人に集中」 |

C が介入実験の本命です。実務のリターゲティングは「効率が良い」とされますが、
それは**もともと買う人に当てているから効率が良く見えるだけ**ではないか、という仮説を
シミュレーションに問わせます。

## 最小スコープ（今回実装した範囲）

- 消費者 8体 × 16ステップ × 3シナリオ（1シナリオあたり LLM 呼び出し 256回）
- ローカル LLM（Ollama / qwen3:4b）。GPU なしでも動く
- 在庫は減る一方（補充・再入荷なし）
- 商品は耐久財として扱い、**1人1回まで購入**。これにより「買ったか / 買わなかったか」の
  2値で世界を突き合わせられる

## やらないこと（時間の都合で捨てたもの）

- 広告主をエージェント化する（配信内容が LLM 任せになり、シナリオ間の統制が崩れるため、
  文面は設定ファイルで固定した）
- 複数回の試行を回して分布を見る（1回の実行例。README の注意書きを参照）
- 価格変更・値引きの動的最適化
- 実データによるキャリブレーション（本作品は完全に架空の市場）

## 壁打ちの要点

1. **「広告 × 増分」はこのシミュレータの構造に合うか？**
   → 合う。本家の fire が「半径内だけが知覚する局所イベント」として実装済みなので、
   その対として「ターゲティングで配信先が決まるイベント」を足せば、広告の本質が入る。
2. **増分をどう測る？**
   → 集団の差ではなく、**個人の対応づけ**で測る。そのためには本家が持っていない
   シード固定が要る。ここが実装の核心になった。
3. **買うかどうかを確率モデルにするか、LLM に決めさせるか？**
   → LLM。確率モデルにすると「広告で購買確率が上がる」と自分で書いたものを
   自分で観測するだけになり、何も分からない。
4. **リターゲティングを介入点にする理由は？**
   → 見かけの数字と実態が最も大きく乖離するはずの施策で、かつ実務で最も広く使われているから。
   ここで乖離が出れば、このプロダクトの主張がそのまま立つ。
