# SD-AgentFoundry-2D

**2D multi-agent social simulation driven by LLM agents**

> 🇯🇵 **日本語版 README はこちらです → [README.ja.md](README.ja.md)**

> This repository is the implementation of **SD-AgentFoundry-2D** described in the manuscript *"Minimal Local Simulation Foundations for LLM- and VLM-Driven Agents in 2D and 3D Environments"* (Ryuki Hyodo).
>
> It is published **not as a finished application, but as a minimal foundation meant to be modified**. It prioritises making the perceive → reason → communicate → act → observe loop **readable and traceable** over covering many features. Everything runs locally (macOS / Windows / Linux), and the LLM runs on a local Ollama server.
>
> It is also used as demo code for social-simulation hackathons.

## Where this fits

SD-AgentFoundry consists of two minimal foundations at different levels of abstraction.

| | This repository (2D) | [SD-AgentFoundry-3D](https://github.com/ryukih/SD-AgentFoundry-3D) |
|---|---|---|
| Driving model | LLM | VLM (vision-language model) |
| Environment | 2D integer grid (a highly transparent environment) | 3D digital twin in USD (JAXA's Kibo module) |
| Input | Numeric state + messages from neighbours (text) | First-person RGB image + dynamically assembled text |
| Focus | Communication and collective behaviour | Visual grounding and embodied action |

The 3D version is published in a separate repository.

The intended users are students, researchers, and practitioners. **The point is to build your own scenarios, agent designs, measurements, and interfaces on top of this**, which is why the machinery is left simple.

## How to interpret the output

The output of this simulation is **not a validated prediction of human behaviour.**

- It is a **tool for generating hypotheses**. It can be used for exploratory work on communication, evacuation, public policy, urban activity, and collective responses to external events, for comparing mechanisms, and for rehearsing possibilities, but backing up any claim about the real world requires separate empirical validation
- The runs and figures included here are **qualitative usage examples**, not controlled evaluations or evidence of predictive validity
- **Descriptions such as "smell", "sound", and "lighting" that appear in the logs are generated by the model, not the state of the simulator.** What exists on the grid is only coordinates, places, capacities, and the numbers describing the fires (keep this in mind when reading `output/messages.jsonl` and `output/memory_reasoning.jsonl`)
- **Exact reproduction is not possible.** Initial positions and personas (gender) are chosen at random on every run, and the current settings have no random-seed entry to fix them

## Overview

A 2D multi-agent simulation **for observing the collective behaviour** of LLM agents running locally. Agents are given only raw numeric data (occupancy rate, fire intensity and distance, and so on); they are never given behavioural instructions or qualitative judgements ("dangerous", "comfortable", and the like). Interpretations such as avoiding, warning, cooperating, or ignoring are **left entirely to the LLM** rather than written into the simulator as rules.

**The field contains several places (by default one cafe on the left and one library on the right), and each place has its own capacity. A fire event also occurs partway through the simulation.**

https://github.com/user-attachments/assets/4fea08be-ea7f-492c-a0eb-414680ed7fae

Demo video: a run near a fire in which the decisions generated went beyond simple evacuation (telling others to regroup, securing supplies, waiting for others, keeping watch). This is **one example observed in one particular run**, not the result of a controlled evaluation ([How to interpret the output](#how-to-interpret-the-output)).

### Fire event

Partway through the simulation, several fires can be started at specified (or random) positions. A fire has the following characteristics:

- **Distance-dependent perception**: only agents inside the fire's perception radius (`radius`) receive the fire information directly. For agents outside the radius, the prompt contains no fire information at all, and they learn of it only indirectly, through messages from other agents
- **Quantitative information only**: an agent is given only the fire's position, intensity (0.0-1.0), radius, and its own distance to it. No qualitative description such as "dangerous" or "should evacuate" is included
- **Constant over time**: the intensity and position of a fire do not change after it starts
- **Nothing before it starts**: prompts for the steps before a fire starts contain no fire section at all

This design lets you observe what behaviour (avoidance, passing on information, ignoring it, and so on) agents produce emergently from quantitative information alone.

Each agent is randomly assigned a **persona (gender: male/female)**, and the gender appears in the LLM prompt and in the information about neighbouring agents. Agents communicate and decide while aware of the other party's gender.

## Setup

### 1. Create and set up the virtual environment

#### macOS/Linux
```bash
# Run the setup script (recommended)
chmod +x setup_mac.sh
./setup_mac.sh

# Or set it up by hand
python3 -m venv venv
source venv/bin/activate
pip install --upgrade pip
pip install -r requirements.txt
```

#### Windows
```cmd
REM Run the setup script (recommended)
setup_win.bat

REM Or set it up by hand
python -m venv venv
venv\Scripts\activate.bat
python -m pip install --upgrade pip
pip install -r requirements.txt
```

### 2. Activate the virtual environment

#### macOS/Linux:
```bash
source venv/bin/activate
```

#### Windows:
```cmd
venv\Scripts\activate.bat
```

### 3. Set up Ollama

#### Install Ollama
   - Install [Ollama](https://ollama.ai/)

#### Start the Ollama server

Ollama normally starts automatically as a background service when installed. If you need to start it by hand, or want to start it explicitly as an API server, follow the steps below:

**Option 1: start it by hand in a separate terminal (recommended)**
```bash
# Open a new terminal and run
ollama serve
```

This starts the server on `http://localhost:11434` by default.

**Option 2: start it in the background (macOS/Linux)**
```bash
ollama serve &
```

**Checking the state of the Ollama server**
```bash
# Check whether the server is up
curl http://localhost:11434/api/tags
```

If it is running correctly, the list of models is returned as JSON.

#### Download and choose a model

**Checking which models are available**:
```bash
# List the models already downloaded into Ollama
ollama list
```

**Downloading a model**:
```bash
# The default model (matches llm.model in config.yaml)
ollama pull qwen3:4b-instruct-2507-q4_K_M

# Examples if you want to use another model
ollama pull qwen3          # A model with thinking output (leave llm.think: false)
ollama pull gpt-oss:20b    # A larger model (needs correspondingly more RAM/VRAM)
```

The default is **a light instruct-style model with no thinking output**. Keep `llm.think: false` even when you use a model that has thinking output, so that the response token budget goes to generating the JSON.

**Choosing the model**:
- The simulation uses the model specified by `llm.model` in `config.yaml`
- **Important**: change `llm.model` in `config.yaml` to the name of a model installed in your own environment:

```yaml
llm:
  model: "qwen3:4b-instruct-2507-q4_K_M"  # Change to the model you want (check with ollama list)
```

**How to specify the model name**:
- **Recommended**: use the form shown by `ollama list` as it is (for example `qwen3:4b-instruct-2507-q4_K_M`)
- **Optional**: when the tag is `:latest`, it can be omitted (for example `qwen3`)
- **Examples**:
  - `qwen3:4b-instruct-2507-q4_K_M` ✅ (the default)
  - `qwen3` ✅ (`:latest` omitted)
  - `gpt-oss:20b` ✅ (a specific tag)

**Notes**: 
- The model matching the name given in `llm.model` in `config.yaml` is the one used
- If the specified model does not exist, an error message is shown when the simulation starts
- Even if several models are downloaded, only the single model specified in `config.yaml` is used
- Using the value in the `NAME` column of `ollama list` as it is the surest approach

### 4. Review the configuration file
   - Check and adjust the parameters in `config.yaml`
   - **In particular, change `llm.model` to the name of a model installed in your own environment** (you can check with `ollama list`)

## Usage

**Notes**: 
- Activate the virtual environment before running
- Make sure the Ollama server is up (run `ollama serve` in a separate terminal)
- Run every command **from the repository root** (the paths for `config.yaml`, `output/`, and the log file are relative to the current directory)

### Basic run

```bash
# Activate the virtual environment (if you have not already)
source venv/bin/activate  # macOS/Linux
# or
venv\Scripts\activate.bat  # Windows

# Run the simulation
python src/main.py
```

Run with no options, the visualisation results are saved as PNG files under `output/`.

- `output/frame_0000.png` — the initial state. It is drawn before the first LLM call, so it appears immediately after startup (within a second)
- `output/frame_0001.png` onwards — at the end of each step

**No window opens.** Drawing always goes to a file (matplotlib's Agg backend), so the results are identical on macOS, Linux, WSL, over SSH, and in CI. If you want to watch a run, open the generated PNG files in an image viewer, or use the [browser viewer](#browser-viewer-viewerhtml) or [video generation](#video-generation-generate_videopy).

> **💡 Tip for your first run**: every agent calls the LLM twice per step, so the more agents and steps you have, and the larger the model, the longer it takes. Start by **trying a small number of agents and steps (`agents.num_agents` and `simulation.duration` in `config.yaml`) with a light model**. Scale up the size and the model once you have confirmed that it works.

> **Difference from the runs in the manuscript**: the bundled `config.yaml` uses `num_agents: 5` so that a first run finishes quickly. The runs in the manuscript (Figure 1 and Table 1) use `num_agents: 20`. Every other setting (the model, `temperature: 0.2`, `think: false`, `max_tokens: 512`, the grid range of ±25, the positions and capacities of the cafe and the library, and the start step, intensity, and radius of the fires) matches the runs in the manuscript.

### Enabling frame saving explicitly

PNG saving is controlled by `visualization.save_frames` in `config.yaml` and is enabled by default. Even if you have set it to `false`, the following option saves frames for that run.

```bash
python src/main.py --save-frames
```

### Using a custom configuration file

```bash
python src/main.py --config custom_config.yaml
```

## Configuration file (config.yaml)

The main parameters:

- **simulation**: simulation settings
  - `duration`: number of simulation steps
  - `half_space_size`: half the size of the space (for example 25 → the coordinate range is -25 to +25)
  - `half_place_size`: half the size of a place (the `half_size` of each place takes precedence)

- **agents**: agent settings
  - `num_agents`: number of agents
  - `communication_radius`: communication radius
  - `memory_limit`: maximum number of memories stored (default: 20)
  - `memory_size`: number of memories used for LLM inference (default: 5)
  - `message_history_limit`: maximum number of messages stored (default: 10)
  - `message_context_size`: number of messages used for LLM inference (default: 3)

- **places**: place settings (several places are supported, and the types can be extended to restaurants, parks, and so on)
  - A list of places. Each place has the following settings:
    - `name`: place name (required, for example "cafe", "library")
    - `type`: place type (required, for example "cafe", "library")
    - `center_x`: X coordinate of the place centre (required)
    - `center_y`: Y coordinate of the place centre (required)
    - `half_size`: half the size of the place (required; the place spans ±half_size from its centre)
    - `capacity`: the capacity of that place (required, used to compute the occupancy rate)

  Example (the current settings):
  ```yaml
  places:
    - name: "cafe"
      type: "cafe"  # Place type: cafe, library, etc.
      center_x: -15
      center_y: 0
      half_size: 5
      capacity: 12
    - name: "library"
      type: "library"
      center_x: 15
      center_y: 0
      half_size: 5
      capacity: 10
  ```

  `type` is mapped to a drawing colour by `place_type_colors` in `src/visualization.py` (`cafe`, `library`, `restaurant`, `park`). A type that is not registered there is given one of the spare colours in order.

- **fires**: fire event settings (several fires are supported)
  - A list of fires. Each fire has the following settings:
    - `name`: name of the fire (required, for example "fire1")
    - `start_step`: the step at which the fire starts (required)
    - `intensity`: intensity of the fire (0.0 to 1.0, passed to agents only as a quantity)
    - `radius`: perception radius (only agents within this distance receive the fire information directly)
    - `center_x`: X coordinate of the fire centre (a random position if omitted)
    - `center_y`: Y coordinate of the fire centre (a random position if omitted)

  ```yaml
  fires:
    - name: "fire1"
      start_step: 35
      intensity: 0.8
      radius: 15
      center_x: 15        # Omit for a random position
      center_y: 10
    - name: "fire2"
      start_step: 70
      intensity: 0.5
      radius: 8
      center_x: -10
      center_y: -10
  ```

- **llm**: LLM settings (see `config.yaml` for details)
  - `model`: Ollama model name
  - `base_url`: Ollama API endpoint
  - `temperature`: sampling temperature (lower gives more consistent behaviour, higher gives more varied behaviour)
  - `think`: whether thinking output is produced (`false` recommended. This project reads only the JSON in the reply, so the thinking part is discarded while still consuming `max_tokens`. Omitting the key follows the model default)
  - `max_tokens`: maximum number of tokens (about 512 is enough with `think: false`)
  - `timeout`: read timeout for a single LLM call [seconds]
  - `repeat_penalty`: repetition penalty (suppresses repeating the same token)
  - `repeat_last_n`: repetition check range (how many tokens are examined for repetition. `0` disables it, `-1` uses `num_ctx`)
  - `min_p`: Min-P sampling (excludes tokens below the given probability)

- **visualization**: visualisation settings
  - `save_frames`: whether to save PNG frames (default: `true`)
  - `frame_interval`: how many steps between saved frames (default: `1`)
  - `output_dir`: output directory (default: `output`. Its contents are deleted at run time)

- **logging**: log settings
  - `level`: log level (`INFO`, `DEBUG`, and so on)
  - `log_file`: path to the log file (standard output only if omitted)

### Coordinate system

This simulation uses **a coordinate system centred on the origin**:

- **Field**: the range `-half_space_size` to `+half_space_size`, centred on the origin (0, 0)
- **Places**: each place has its own centre (`center_x`, `center_y`) and spans `±half_size` from that centre (inclusive)

**What agents know**:
- Agents know **the positions of all places** (they are included in the prompt)
- The occupancy of a place (number of agents, capacity, occupancy rate), however, is received directly only by the agents inside that place

**About choosing the model**:
- Specify the model to use with `llm.model` in `config.yaml`
- To see the available models: `ollama list`
- To download a model: `ollama pull <model name>`
- **The default is the light `qwen3:4b-instruct-2507-q4_K_M`**, which works as it is in most environments. **If you want to observe higher-quality emergence, a larger model such as `gpt-oss:20b` is recommended** (it needs correspondingly more RAM/VRAM)
- If you use a model with thinking output (something other than instruct, such as `qwen3`), keep `llm.think: false`. The thinking part is discarded in this project, so leaving it enabled can use up `max_tokens` on thinking alone and leave the reply empty

## Output

- `output/`: the visualisation frames (`frame_*.png`) are saved here
  - The visualisation shows an agent's **gender as colour** (male = blue, female = red) and **whether it is inside or outside a place as the marker shape** (inside = ★, outside = ●)
  - After a fire starts, **the centre of each fire (red triangle)** and **its perception radius (dashed circle)** are drawn (several fires are supported). The area of a fire is filled using **a colour map (YlOrRd)** according to its intensity, and the **colour bar (0.0 to 1.0, "Intensity of Fire")** shown permanently on the right lets you read the intensity
- `output/messages.jsonl`: the history of messages between agents (useful for analysing how fire information propagates)
- `output/memory_reasoning.jsonl`: the memory and reasoning log of the agents
- `simulation.log`: the simulation log

## LLM agent design

### Basic design

- Every step, each agent generates **Message / Memory / Action** from the LLM and acts synchronously
- All agents share the same LLM engine; the only differences are their own Memory and interaction history (individuality emerges from that history)
- The prompt does not state any "optimisation task"; it gives a description of the situation, numeric data, messages from neighbours, and the agent's own state
- **There are two LLM calls per step** (the communication prompt in Phase 1 and the action-decision prompt in Phase 3). Replies are asked for in JSON, and if parsing fails, a conservative fallback parser takes over
- The full prompt templates are given in Appendix A.1 of the manuscript

### Persona (gender)

- Each agent is randomly assigned **male** or **female** at initialisation (with probability 1/2 each)
- The gender appears at the start of the LLM prompt (`You are Agent N (male/female)`) and in the self-state field (`Gender:`)
- The other party's gender is also shown in the information about neighbouring agents (for example `Agent 3 (female) is outside the places`)
- Agents decide what to say and how to act while aware of the other party's gender

### Action

A discrete choice among four directions, plus staying put:
- `up`: Y+1 (upwards)
- `down`: Y-1 (downwards)
- `left`: X-1 (to the left)
- `right`: X+1 (to the right)
- `stay`: stay at the current position

### Memory

- The `memory` field emitted by the LLM is fed back as the "Previous Memory" of the next step
- This is the mechanism by which internal state evolves depending on history and individuality emerges
- `memory_limit`: maximum number of memories stored (the oldest are dropped first)
- `memory_size`: number of recent memories referred to during LLM inference

### Information available only inside a place

**Only the agents inside a place** receive the following numeric data directly:
- **The current number of agents** (Number of agents here)
- **The capacity** (Capacity)
- **The occupancy rate** (Occupancy rate = number of agents / capacity)

No qualitative judgement (comfortable, uncomfortable, and so on) is included; interpreting the numbers is left to the agent itself.

**Agents outside a place** do not receive this information (they learn it indirectly, through conversation and reasoning)

**Note**: agents know the positions of all places, but the occupancy of each place can be known only by the agents inside it.

### Communication

- Messages can be exchanged between agents within the communication radius (default: 5 cells)
- **Same-region condition**: communication is possible only between agents that satisfy one of the following
  - **both are outside any place**, or
  - **both are inside the same place**

  **Communication limits**:
  - ❌ An agent inside a place ↔ an agent outside a place: **not possible**
  - ❌ Agents inside different places: **not possible**
  - ✅ Agents inside the same place: **possible**
  - ✅ Agents that are both outside any place: **possible**

- `message_history_limit`: maximum number of messages stored (the oldest are dropped first)
- `message_context_size`: number of recent messages referred to during LLM inference

### Order of execution within a step

Each step runs in the following order:

0. **Fire activation check** — for each fire, if `step >= start_step`, start the fire at the specified (or a random) position (once per fire)
1. **Phase 1: decide messages** — every agent decides its message with the LLM (agents within the perception radius of a fire are given that fire's information)
2. **Phase 2: send messages** — send the message to the agents that were neighbours at the moment of the decision
3. **Phase 3: decide actions** — every agent decides its action (move/stay) with the LLM (fire information included)
4. **Phase 4: apply movement** — each agent moves in the direction it decided

Because of this order, messages are sent based on the positions before the movement.

### LLM output format

**Deciding a message (Phase 1)**:
```json
{
    "message": "message to nearby agents (optional, max 200 words)",
    "reasoning": "reason for sending the message"
}
```

**Deciding an action (Phase 3)**:
```json
{
    "action": "move" or "stay",
    "direction": "up", "down", "left", or "right",
    "memory": "what you want to remember for the next step",
    "reasoning": "reason for the decision"
}
```
